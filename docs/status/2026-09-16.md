## Current state

The native Windows AMD path remains centered on Tauri/React, a persistent Python worker, Hunyuan3D-2 Mini for Shape and Hunyuan Paint for Texture. RX 6950 XT / gfx1030 remains the hardware acceptance target.

The original `mesh-cleanup-v1` heuristic path was superseded by PyMeshLab/Manifold3D based game-ready preparation. The current cleanup line has since received additional runtime, performance and UI hardening based on real hardware testing.

## Game-ready cleanup hardening after the first RX 6950 XT test

A real `Mesh → Game-ready → Auto` run on a roughly 534k-triangle Hunyuan mesh exposed two user-visible failures: the UI could become completely black while the job was active, and Auto cleanup could spend many minutes evaluating successive QEM/Hausdorff candidates.

The current branch contains the following fixes:

- Mesh cleanup explicitly evicts cached Hunyuan Shape and Texture pipelines before CPU-only mesh work, releasing Radeon VRAM instead of keeping the ML model resident unnecessarily.
- The Three.js viewer is not instantiated while a job is busy, so cleanup does not compete with the worker for a WebGL context.
- WebGL renderer creation, render failures and `webglcontextlost` are handled without tearing down the React application.
- Viewer/WebGL failures are written to the persistent diagnostic log.
- React crash diagnostics are preserved instead of leaving an unexplained blank surface.
- Heavy cleanup now reports detailed progress stages instead of remaining on a generic `Cleaning mesh…` message.
- Adaptive reduction cost is bounded:
  - progressive QEM reduction reuses the previously accepted candidate;
  - Auto targets halve rather than shrinking in many small 0.70 steps;
  - Hausdorff sampling is bounded to 4k–12k samples rather than scaling to 50k;
  - Game-ready uses a safer 6000-triangle Auto floor;
  - Aggressive retains its lower 1500-triangle floor.
- Healthy, watertight, single-component Game-ready input can skip geometry-changing remeshing before reduction.

These changes are covered by automated tests and the latest complete CI is GREEN. They still require a fresh RX 6950 XT hardware acceptance run on the representative steak mesh.

## Current Game-ready behavior

`Light` remains conservative.

`Game-ready` currently uses:

- PyMeshLab topology repair when needed;
- duplicate/null face and duplicate vertex cleanup;
- non-manifold repair;
- small component removal;
- hole closing;
- optional isotropic remeshing for unhealthy topology;
- progressive QEM decimation;
- symmetric Hausdorff error scoring against the repaired reference;
- Auto triangle budget with a 6000-triangle floor;
- Manual triangle target override.

`Aggressive` follows the same general pipeline with stronger repair/reduction settings and a 1500-triangle floor.

## Progress and inspection UX

The mesh workflow now streams detailed heavy-cleanup progress through Python → persistent worker → Rust/Tauri → React. Stages include repair, reduction attempts and validation.

The model viewer now provides:

- Before / After comparison for cleaned meshes;
- Solid;
- Wireframe;
- Solid + Wire inspection modes;
- graceful WebGL failure handling.

The mesh action remains available while Advanced controls are open through the revised panel layout.

## Startup/runtime UX

Startup work has progressed beyond the 2026-09-13 checkpoint:

- startup probes were moved off the Tauri UI thread;
- a dedicated runtime loading surface is shown while initialization is occurring;
- development runs synchronize the current source worker into the persistent runtime before Tauri/Vite startup, preventing stale-worker tests;
- the app keeps startup/runtime diagnostics visible rather than looking frozen.

This improves the original complaint that the application appeared hung while Hunyuan initialized. A fully native pre-main-window splash can still be revisited later if the current loading surface is not sufficient in packaged builds.

## Texture pipeline changes since the previous checkpoint

The branch also gained:
